# Z3r0 Baseline at v0.3.1 (Project Workbench Traffic, Credentials, and Sandbox Readiness)

Date: `2026-11-19`
Status: `current dual-baseline snapshot`
Supersedes: `docs/aegis/baseline/2026-11-19-p0-p1-runtime-guards-and-traffic.md`
ADR: `docs/aegis/adr/ADR-0001-flow-is-a-separate-aggregate.md`

## 1. Purpose

Record product and architecture truth at v0.3.1 after the work project
workspace gained Traffic and Credentials views with exchange-to-evidence
conversion, Playground gained session token usage, and the built sandbox image
was accepted end to end against the control plane.

## 2. Product / Requirement Baseline

### 2.1 Current Truth

- Operators launch autonomous Flows on `/flows` against a running sandbox; the
  controller advances plan -> subtask -> `ask`/`done` -> report.
- Session and Flow summaries expose cumulative LLM request counts and input,
  output, cached, and total tokens. Playground shows them per session in the
  session list and header, including project sessions.
- Operators and agents store task or project credentials in the Credentials
  Vault; active credentials are injected into subsequent turns. The work
  project workspace lists the credentials saved on the project and in its
  sessions, with masked secrets, reveal, copy, and delete.
- Destructive shell, SQL, and HTTP commands are intercepted by Command Guard.
  Approvals apply once to the exact intercepted command and can only be granted
  by an authenticated operator turn or Flow input reply.
- Sandbox HTTP and HTTPS egress exchanges are decrypted with a sandbox-local
  MITM root CA, synced periodically into PostgreSQL, scoped to container and
  work project ownership, and searchable via `/api/traffic` and agent tools.
- The work project workspace lists the exchanges of the project and its bound
  sandbox with full-text, path, method, and status filters. An exchange converts
  into immutable `http_exchange` evidence on a non-terminal work item.
- A started sandbox container is reported as running once its control proxy
  answers and the stored egress policy is applied. A container whose control
  proxy does not answer within 60 seconds is stopped and the start fails.
- Optional FOFA asset search (`fofa_search`) is mounted when enabled and
  configured in system settings.

### 2.2 Non-negotiables

1. Authorized-scope operation only; no unsandboxed host execution
2. Tenant isolation on sessions, Flows, work projects, credentials, and captured traffic
3. Command Guard grants are operator-issued, exact-command, and one-shot
4. Flow progression is owned by `core/flow/controller.py`
5. Real proxy, database, and runtime errors surface without silent suppression
6. Evidence created from captured traffic is immutable and bound to a work item

## 3. Architecture / Runtime Boundary Baseline

### 3.1 Current Truth

- Chat owner: `core/runtime/session.py` (`AgentSession`)
- Flow owner: `core/flow/controller.py` + `service/flow/`
- Token Ledger owner: `service/agent/session_state.py` (`record_session_usage`)
- Credentials Vault owner: `service/agent/credentials.py` + `core/tools/credentials.py`
- Command Guard owner: `core/sandbox/command_guard.py`
- Traffic capture owner: `sandbox/proxy/mitm.go` + `sandbox/proxy/traffic.go` + `service/sandbox/traffic.py` + `core/tools/traffic.py`
- Project workbench records owner: `router/work_project/records.py` + `service/work_project/records.py`
- Sandbox start and readiness owner: `service/sandbox/lifecycle.py` + `service/sandbox/control_proxy.py`
- Persistence: PostgreSQL via SQLModel (`0.3.1`)

### 3.2 Contracts

- Project records: `GET|POST /api/work-projects/{id}/credentials`,
  `DELETE /api/work-projects/{id}/credentials/{credential_id}`, and
  `POST /api/work-projects/{id}/traffic/{traffic_id}/evidence`. Project traffic
  is read through `/api/traffic?project_id=`.
- Traffic pull: `GET /traffic?after_seq=&boot_id=` on the sandbox control proxy
  returns `boot_id`, `items`, and `last_seq`. Sequence numbers restart with the
  proxy process; a cursor from another boot returns every buffered entry. The
  control plane stores `(proxy_boot, proxy_seq)` per row and pulls every 3
  seconds for running containers.
- Capture: the proxy buffers 2000 exchanges with 64 KiB per body, decodes
  `gzip` and `deflate`, and records an empty body for binary payloads and other
  content codings. Requests are forwarded with `Accept-Encoding` limited to
  `gzip`, `deflate`, and `identity`.
- Storage: captured text is stored without NUL bytes and unpaired surrogates.
  `create_all_tables` adds `sandbox_traffic_entries.proxy_boot` on startup.
- Sandbox entrypoint: load or generate the CA, install it into the system
  bundle and the Chrome NSS database, then start `supervisord`; the control
  proxy answers `/healthz` only after the CA is installed.
- Container start: the control plane starts the Docker container, waits for
  `/healthz`, posts the egress environment, and then records `RUNNING`.

## 4. Known Limits

- Exchanges captured after the last pull before a container stops are not
  persisted, and a pull that overlaps a container stop logs a warning.
- Chrome background requests to its vendor services appear in captured traffic.
- The sandbox image targets amd64. On arm64 hosts it builds and runs under
  emulation with `docker build --platform linux/amd64`; ptrace-based tools are
  unverified there.
