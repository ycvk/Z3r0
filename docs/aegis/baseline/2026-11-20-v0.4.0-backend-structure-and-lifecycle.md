# Z3r0 Baseline at v0.4.0 (Backend Structure, Guardrails, and Record Lifecycle)

Date: `2026-11-20`
Status: `current dual-baseline snapshot`
Supersedes: `docs/aegis/baseline/2026-11-19-v0.3.1-project-workbench-and-sandbox-readiness.md`
ADR: `docs/aegis/adr/ADR-0001` through `ADR-0007`

## 1. Purpose

Record product and architecture truth at v0.4.0. The release keeps the
feature set of v0.3.1 and changes how the backend is built: one import
direction, one place for access rules and for error mapping, credentials and
traffic as their own domains, migrations, a lock file, and CI. It also defines
what happens to credentials and Flows when the records they depend on are
deleted, and keeps operator approvals across a restart.

## 2. Product / Requirement Baseline

### 2.1 Current Truth

- The v0.3.1 feature set is unchanged: Flows on `/flows`, token usage per
  session and Flow, the Credentials Vault, Command Guard, decrypted HTTP and
  HTTPS traffic capture, the work project Traffic and Credentials views, and
  exchange-to-evidence conversion.
- A record addressed by id answers 404 both when it does not exist and when
  the caller may not use it. 403 is returned for role gates: admin-only routes
  and assigning another user as the owner of a new container.
- A credential belongs to one vault: the work project it was recorded in, or
  the agent session when there is no project. Deleting the project or the
  session deletes the vault. Deleting the user who recorded a credential keeps
  it.
- A Flow is deleted with its session. Deleting a user deletes the Flows they
  started outside a work project; their Flows inside a project stay, unfinished
  ones are cancelled, and each passes to the user who takes over its session.
  Deleting a work project deletes its Flows. A sandbox container cannot be
  deleted while an unfinished Flow uses it; a finished Flow stays without it.
- A Command Guard approval and the operator's answer to a waiting Flow still
  apply after the backend restarts.
- The application applies its database migrations at startup and adopts a
  database created before migrations existed.

### 2.2 Non-negotiables

1. Authorized-scope operation only; no unsandboxed host execution
2. Tenant isolation on sessions, Flows, work projects, credentials, and captured traffic
3. Command Guard grants are operator-issued, exact-command, and one-shot
4. Flow progression is owned by `service/flow/controller.py`
5. Real proxy, database, and runtime errors surface without silent suppression
6. Evidence created from captured traffic is immutable and bound to a work item
7. Backend packages import downward only; CI fails on a violation

## 3. Architecture / Runtime Boundary Baseline

### 3.1 Current Truth

- Layer order: `router`, `handler` and `tools`, `service`, `middleware`,
  `core`, `model`, `schema`, `utils`
- Runtime installation owner: `app.py` (`install_agent_runtime`) with
  `core/runtime/ports.py` and `core/runtime/coordination.py`
- Chat owner: `core/runtime/session.py` (`AgentSession`)
- Agent tool owner: `tools/`, mounted per agent by `tools/catalog.py`
- Flow owner: `service/flow/controller.py` (progression), `service/flow/records.py`
  (persistence), `service/flow/lifecycle.py` (deletion), `service/flow/runs.py`
  (controller tasks)
- Access owner: `service/common/access.py`
- Error owner: `core/errors.py` + `middleware/common/response.py`
- Token Ledger owner: `service/agent/session_state.py` (`record_session_usage`)
- Credentials Vault owner: `service/credential/` + `tools/credentials.py`
- Command Guard owner: `core/sandbox/command_guard.py`
- Traffic owner: `sandbox/proxy/mitm.go` + `sandbox/proxy/traffic.go` +
  `service/traffic/` + `tools/traffic.py`
- Project workbench records owner: `router/work_project/records.py` + `service/work_project/records.py`
- Sandbox start and readiness owner: `service/sandbox/lifecycle.py` + `service/sandbox/control_proxy.py`
- Persistence: PostgreSQL via SQLModel; schema owner `migrations/versions` (`0001` to `0004`)
- Dependency owner: `pyproject.toml` + `uv.lock`

### 3.2 Contracts

- Imports: three `lint-imports` contracts. Layers import downward only;
  `router` and `handler` do not import `model`; `service.credential` and
  `service.traffic` do not import `service.agent`, `service.flow`, or
  `service.work_project`.
- Errors: services raise a `DomainError` subclass. `ValidationError` 400,
  `AuthenticationError` 401, `ForbiddenError` 403, `NotFoundError` 404,
  `ConflictError` 409, `UpstreamError` 502, each rendered as
  `CommonResponse`. Agent tools turn a `DomainError` into an error tool result.
- Runtime: `install_agent_runtime()` installs `RuntimePorts`,
  `RuntimeCoordination`, and the session pool; using any of them before that
  raises.
- Schema: revisions `0001` baseline, `0002` credential vault ownership,
  `0003` Flow deletion rules, `0004` stored Command Guard state and Flow input.
  `tests/test_migrations.py` fails when models and revisions differ.
- Stored operator state: `sandbox_guarded_commands` holds the pending command
  and one-run approvals of a session; `flows.pending_input` holds the answer to
  a waiting Flow until the controller takes it.
- API changes since v0.3.1: `SessionCredentialSchema.session_id` and the
  `sandbox_container_id` of a Flow are nullable; deleting a sandbox container
  can answer 400; record endpoints answer 404 where some answered 403.
- Checks: `ruff`, `lint-imports`, `basedpyright` against a baseline that only
  shrinks, `pytest` on PostgreSQL, the `sandbox-proxy` Go checks, sandbox skill
  validation, the API contract sync check, and both frontend builds, all run by
  `.github/workflows/ci.yml`.
- The sandbox proxy, entrypoint, and image contracts of v0.3.1 are unchanged.

## 4. Known Limits

- Startup needs network access once: LightRAG downloads a tokenizer file, and
  the application does not start when that download fails.
- Credential secrets are stored in plaintext in PostgreSQL.
- Captured traffic has no retention policy and stays after its container or
  work project is deleted.
- Process-local state (background loop handles, work in flight, locks,
  caches) assumes one backend process.
- The frontend has no automated tests. The Flow pages for a Flow whose
  container was deleted were type-checked and built, not viewed in a browser.
- Exchanges captured after the last pull before a container stops are not
  persisted, and a pull that overlaps a container stop logs a warning.
- The sandbox image targets amd64. On arm64 hosts it builds and runs under
  emulation; ptrace-based tools are unverified there.
